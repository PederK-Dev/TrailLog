# TrailLog

A REST API for logging hikes — built with FastAPI, SQLAlchemy, and SQLite, with full CRUD functionality and a CI/CD deployment pipeline to Azure App Service via GitHub Actions.

Built as a personal project to get hands-on experience with Python, REST API design, and cloud deployment.

## Features

- Full CRUD for trail entries (create, read, update, delete)
- Data validation with Pydantic schemas, separated from the database models
- Aggregate endpoints: total distance logged, and longest trail
- Proper REST conventions: request bodies for create/update, path parameters for lookups, correct HTTP status codes (including 404 handling for missing trails)
- Interactive API documentation via Swagger UI (auto-generated by FastAPI)
- CI/CD pipeline via GitHub Actions, deploying to Azure App Service

## Tech stack

- **Backend:** Python, FastAPI
- **Database:** SQLAlchemy ORM, SQLite (local)
- **Validation:** Pydantic
- **Server:** Uvicorn
- **Deployment:** Azure App Service, GitHub Actions (CI/CD)

## API overview

| Method | Route                          | Description                                |
| ------ | ------------------------------ | ------------------------------------------ |
| GET    | `/`                            | Health check — confirms the API is running |
| POST   | `/trails`                      | Create a new trail entry                   |
| GET    | `/trails`                      | List all trails                            |
| GET    | `/trails/{trail_id}`           | Get a single trail by ID                   |
| PUT    | `/trails/{trail_id}`           | Update an existing trail                   |
| DELETE | `/trails/{trail_id}`           | Delete a trail                             |
| GET    | `/trails/stats/total-distance` | Total distance across all logged trails    |
| GET    | `/trails/stats/longest`        | The single longest trail logged            |

A trail has: `place`, `date`, `distance_km`, `duration_minutes` (optional), and `notes` (optional).

## Design notes

**Schemas vs. models.** `models.py` defines the actual database table structure. `schemas.py` defines the shape of data going in and out of the API (`TrailCreate` for incoming data, `TrailOut` for outgoing data, which adds the database-assigned `id`). Keeping these separate means the API's public contract can evolve independently of the underlying database structure.

**Request body over query parameters.** Create and update endpoints take a JSON request body rather than query parameters, which is the correct REST convention for submitting data — and avoids sensitive/lengthy data ending up in server access logs via the URL.

**Error handling.** Endpoints that look up a specific trail by ID return a proper `404 Not Found` with a clear message when the trail doesn't exist, rather than failing silently or returning malformed data.

## What I learned

- How FastAPI's type hints double as automatic request validation and API documentation, with very little boilerplate.
- The practical difference between an ORM's role (SQLAlchemy, describing the database) and a validation library's role (Pydantic, describing the API's data contracts) — and why keeping them as separate schemas, rather than reusing one for both, keeps the API's public contract independent of the database structure.
- REST conventions in practice: which HTTP verb and parameter style (path, query, or body) fits which kind of operation, and why.
- Real constraints of cloud deployment: configuring a startup command, binding to `0.0.0.0` instead of `localhost` so the app accepts external traffic, and working within Azure App Service's free-tier (F1) compute quota.
